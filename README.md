# Crewbus

Локальный чат с одним агентом и четырьмя инструментами задач: создание, чтение, изменение и удаление. pi управляет провайдерами и агентным циклом; AI Elements и shadcn/ui отвечают за представление. AI Elements не заменяют pi и не требуют AI SDK `useChat`: Crewbus использует свой HTTP/SSE протокол и одноимённый локальный React hook.

Нужны Node.js **24.21.0**, pnpm **12.6.0**; для контейнеров — Docker с BuildKit и Compose. Проверенный bootstrap поддерживает Linux x64 glibc и Windows x64. Windows descriptor закреплён, но запуск приложения на Windows здесь не проверялся. Команды ниже предназначены для bash.

```bash
node scripts/bootstrap-pnpm.mjs /tmp/crewbus-pnpm
export PATH="/tmp/crewbus-pnpm/bin:$PATH"
pnpm install --frozen-lockfile
```

Установка проверяет минимальный возраст релиза **14 дней**, наличие даты, trust/provenance без downgrade, запрещает экзотические транзитивные зависимости и неразрешённые build scripts. Версии точные, lockfile обязателен; исключения и разрешённые сборки явно записаны в `pnpm-workspace.yaml`. Не отключайте политики ради установки. Bootstrap проверяет независимый SHA512 платформенного pnpm до исполнения.

Для разработки запустите в двух терминалах из корня:

```bash
pnpm dev:server
```

```bash
pnpm dev:web
```

Откройте http://127.0.0.1:5173. Vite проксирует API на порт 3000. Создайте диалог, выберите провайдера, сохраните его API-ключ в форме и выберите модель. Ключ можно заменить или удалить в настройках; API возвращает только признак настройки. Ключ не передаётся браузеру обратно и не хранится в localStorage.

Основной способ запуска — Node напрямую, в том числе внутри sbx. Production обслуживает UI и API с одного origin:

```bash
pnpm build
export CREWBUS_DATA_DIR="$HOME/.local/share/crewbus"
NODE_ENV=production pnpm start
```

Откройте http://127.0.0.1:3000. Для подключения извне задайте `HOST=0.0.0.0` при запуске; адрес — `http://<адрес-среды>:3000`. В sbx также нужен опубликованный порт sandbox. `pnpm build` сам обновляет `apps/server/public` из веб-сборки, удаляя старые файлы; не используйте этот каталог для собственных файлов. Dev frontend обслуживает Vite. Данные находятся вне checkout по указанному абсолютному пути и сохраняются при пересборке.

Docker — дополнительный способ поставки, для разработки и работы Crewbus он не требуется. Образ использует один закреплённый по digest Node image и непривилегированного пользователя:

```bash
export NODE_IMAGE="$(cat .docker/node-image.txt)"
docker compose up --build
```

Compose публикует `0.0.0.0:3000`, сервер контейнера слушает `0.0.0.0:3000`; извне открывайте `http://<адрес-хоста>:3000`. Данные — named volume `crewbus-data` в `/data`. Один серверный процесс/реплика на одну базу. `/api/health` проверяет доступность SQLite. `docker compose down` сохраняет volume; `down -v` удаляет данные.

Без Docker данные по умолчанию находятся в `.crewbus` относительно рабочего каталога серверного процесса (для команд pnpm выше — `apps/server/.crewbus`). Можно задать абсолютный `CREWBUS_DATA_DIR`; также доступны `HOST` (по умолчанию 127.0.0.1) и `PORT` (3000). В SQLite находятся история, задачи и **API-ключи в открытом виде**; ограничьте доступ к каталогу и резервным копиям. Приложение рассчитано на одного владельца, без пользовательской аутентификации. Не публикуйте его в интернете.

Для backup остановите сервер (`Ctrl+C` либо `docker compose stop`), скопируйте **весь** каталог данных/содержимое volume в защищённое место, затем запустите сервер. Восстанавливайте при остановленном сервере, сохраняя владельца каталога (в контейнере пользователь node). Не копируйте только основной SQLite файл во время записи. Graceful shutdown сначала останавливает запуски, затем закрывает базу.

При переходе с Docker остановите контейнер, скопируйте весь `/data` в защищённый каталог и укажите его в `CREWBUS_DATA_DIR` при прямом запуске. Сохраните исходный volume до проверки переноса. Не запускайте одновременно два сервера с одной базой; старый volume после переноса больше не обновляется.

В одном диалоге работает один запуск; другие диалоги могут работать одновременно. Во время запуска ручные изменения задач и смена модели блокируются. Лимиты: 20 обращений к модели, 5 минут, сообщение до 16 000 символов, заголовок задачи 1–500 символов после trim. Остановка сохраняет уже выполненные действия. Reload/reconnect продолжают отображение без нового model request. После сбоя запуск помечается прерванным; сохранённый результат инструмента восстанавливается, автоматического повтора/auto-resume нет. Следующее сообщение — явное действие владельца.

Автоматические проверки не требуют настоящего ключа:

```bash
pnpm typecheck
pnpm test
pnpm build
node scripts/verify-ui-provenance.mjs
pnpm audit --prod --audit-level=high
pnpm exec playwright install --with-deps chromium
pnpm exec playwright test
node scripts/docker-smoke.mjs
```

Browser suite использует отдельный faux сервер и временную базу, один worker, порты 3000/5173 должны быть свободны. Production не имеет тестовых/debug endpoints. Docker smoke выполняет clean build, проверяет health/non-root/API404/UI и сохранение chat/todo IDs после пересоздания контейнера на собственном временном volume, затем удаляет только свои ресурсы. Live compatibility с реальным провайдером **не проверена**: реальный ключ не предоставлялся. Faux проверки не подтверждают внешнюю доступность или тарифы провайдера.

Решения и ограничения реализации сохранены в [implementation notes](docs/superpowers/2026-10-15-implementation-notes.md); [индекс контекста](docs/README.md) связывает спецификацию и источники. Provenance UI закреплён в `docs/ui-provenance.json`: проверяются оригиналы, рабочие hashes, upstream SHA/URL и лицензии. Изменяйте рабочий hash только осознанно вместе с source diff.

MVP не имеет coding tools, MCP или дочерних агентов. TodoPort, RunManager и события дают основу для будущей оркестрации, но её безопасность, полномочия и протоколы потребуют отдельного проектирования. Большие Markdown/Shiki/Mermaid bundles остаются известным ограничением производительности; предупреждение сборки не скрывается.
