# Crewbus MVP: веб-чат на pi

Создано: 2026-10-09. Финальная редакция для просмотра: 2026-10-12. Статус: готово к согласованию; одобрение полной спецификации ещё не получено, реализация не начата.

## Кратко для согласования

Минимальная версия — сохраняемый веб-чат с выбором провайдера, API-ключом, стримингом ответа, остановкой агента и четырьмя todo-инструментами. Серверный агент работает на pi-ai/pi-agent-core; интерфейс — React/Vite, shadcn/ui и выборочные AI Elements. Субагенты относятся к следующему этапу.

Стек и назначение согласованы в обсуждении. Режим использования, область тудушек, упаковка и числовые лимиты ниже — предлагаемые настройки MVP; согласование этой спецификации включает их принятие либо явную корректировку. Точные контракты реализации будут раскрыты в отдельном плане после согласования.

## Цель

Собрать минимальное приложение с веб-чатом и одним агентом на основе pi. Агент получает только инструменты тудушек. В дальнейшем этот агент станет управляющим агентом: сможет запускать других агентов, выдавать им задания и наблюдать результаты.

Первый сквозной сценарий: пользователь выбирает провайдера и модель, вводит API-ключ, пишет «Создай задачу изучить pi». Агент вызывает `todo_create`, задача появляется в панели, агент сообщает о результате. После перезапуска приложения диалог и задача сохраняются.

## Согласованные решения

- Интерфейс: веб-чат.
- Язык: TypeScript.
- Сервер: Node.js 24 LTS + Fastify.
- Клиент: React + Vite, Tailwind CSS 4, shadcn/ui + AI Elements.
- Хранилище: SQLite.
- Менеджер пакетов: pnpm с выдержкой публикаций 14 дней и дополнительными ограничениями цепочки поставок.
- Подключение модели: выбор провайдера и модели, ввод API-ключа. Провайдерные протоколы реализует pi.
- Набор инструментов агента формирует Crewbus; стандартные инструменты coding agent не подключаются.

## Предлагаемые настройки MVP

Это конкретные предложения для просмотра, а не ранее согласованные требования.

| Настройка | Предлагаемое значение | Следствие |
| --- | --- | --- |
| Режим использования | Один владелец, локальное приложение | Учётные записи и публикация в интернете не входят в MVP |
| Диалоги | Несколько сохраняемых диалогов, один активный запуск в каждом | Другая отправка в занятый диалог блокируется; разные диалоги могут работать одновременно |
| Область тудушек | Конкретный диалог | Агент и ручная панель используют один список, изолированный от других диалогов |
| Упаковка | Один Docker-контейнер с постоянным томом; также запуск через pnpm | Один серверный процесс обслуживает UI, API и SQLite |
| Лимит запуска | 20 обращений к модели, 5 минут | Защита от бесконечной цепочки инструментов; причины остановки видны в UI |
| Размеры ввода | Сообщение до 16 000 символов; заголовок задачи 1–500 символов после trim | Сервер отклоняет невалидный ввод до изменения состояния |

## Границы версии

В MVP входят настройка API-ключа, выбор модели, диалоги и история, стриминг и остановка, четыре todo-инструмента, ручная панель задач, восстановление после перезапуска и локальная упаковка.

Инструменты других агентов, OAuth, произвольные MCP-серверы, загрузка файлов, голос, RAG, расписания, автоматическое выполнение фоновых задач и сжатие контекста относятся к следующим версиям. При переполнении контекста предлагается новый диалог. Автоматическое возобновление запусков или повторение инструментов после сбоя не входит в MVP.

## Выбор способа интеграции с pi

| Вариант | Что получаем | Цена для MVP |
| --- | --- | --- |
| **pi-ai + pi-agent-core, собственный небольшой сервер** | Провайдеры, агентный цикл, собственный набор инструментов, поток событий | Нужно реализовать HTTP API и хранение состояния. Рекомендуется |
| SDK pi-coding-agent с отключёнными стандартными инструментами | Дополнительная инфраструктура сессий и coding agent | Нужно контролировать обнаружение расширений, ресурсов и поведение coding agent |
| Экспериментальные pi-server / pi-client | Готовые части сервисного протокола pi | Больше компонентов и экспериментальных контрактов для простого веб-чата |
| pi-web-ui | Готовые web components на mini-lit/Lit, чат, выбор модели, ключи, карточки инструментов и пример приложения | Последний опубликованный пакет 0.75.3 использует pi-ai ^0.75.3, браузерное хранилище и прямую URL-зависимость xlsx; требует проверки совместимости, адаптации к серверному агенту и изменения дерева зависимостей для нашей политики |

Выбираем первый вариант. Используем опубликованные пакеты pi, локальный клон нужен для изучения API. Fork pi и зависимость на Git-ветку не требуются.

Веб-интерфейс собирается на согласованном React/Vite с компонентами shadcn/ui и AI Elements. У pi есть отдельная библиотека `@earendil-works/pi-web-ui` с примером приложения; её последний опубликованный релиз — `0.75.3`. Это вариант для переиспользования UI, который нужно отдельно адаптировать к нашей архитектуре. В изученном теге pi `v0.87.1` пакета `packages/web-ui` уже нет. Существование библиотеки не означает наличия готового серверного веб-чата в выбранных pi-ai/pi-agent-core.

## Архитектура

```text
React / Vite
    │ HTTP: настройки, диалоги, запуск, остановка, тудушки
    │ SSE: события конкретного запуска
    ▼
Fastify
    ├── настройки провайдеров → pi-ai Models → провайдер модели
    ├── менеджер диалогов и запусков → pi-agent-core Agent
    │                                 └── реестр инструментов → сервис тудушек
    └── SQLite: настройки, credentials, диалоги, сообщения, запуски, события,
                тудушки и сохранённые результаты их инструментов
```

В production Fastify обслуживает и API, и собранные статические файлы Vite. Клиент и API используют один origin. В development Vite проксирует `/api` на Fastify.

### Веб-интерфейс и AI registries

Выбранная основа UI — React/Vite, Tailwind CSS 4, shadcn/ui и AI Elements. shadcn предоставляет компоненты настроек, навигации и панели тудушек; AI Elements — компоненты чата и отображения работы агента. Сравнение по документации и фактическим registry JSON:

| Источник | Что подходит Crewbus | Особенности интеграции |
| --- | --- | --- |
| prompt-kit | Chat Container, Prompt Input, Message, Tool | Проверенные Chat Container, Prompt Input и Tool не зависят от `ai` или `@ai-sdk/react`; Message дополнительно приносит Markdown-библиотеки и подсветку кода |
| **AI Elements — выбран** | Conversation, Message, Prompt Input, Tool, Model Selector; далее Reasoning, Plan, Task, Queue, Agent | Богатый единый набор компонентов. Проверенные Message, Tool и Prompt Input используют типы из пакета `ai`; адаптер событий pi связывает их с нашим сервером. Проверенные Conversation и Model Selector от `ai` не зависят |
| assistant-ui | Готовая инфраструктура чата с собственным backend; отдельные Elements для инструментов, активности, плана и субагентов | Для полного чата есть ExternalStoreRuntime с сообщениями и callbacks нашего сервера. Проверенные standalone Elements Tool Call, Agent Plan и Subagent List не импортируют этот runtime и пригодны для дальнейшего развития |

Для первой версии выбираем shadcn/ui + выборочные компоненты AI Elements: Conversation, Message, Prompt Input, Tool и Model Selector, включая необходимые registryDependencies. Остальные элементы подключаются при появлении соответствующих возможностей. Это даёт единый визуальный набор для MVP и будущего гипервизора.

Клиентский адаптер событий Crewbus передаёт текст сообщения в Message, состояние запуска — в Prompt Input, аргументы и результат вызова — в Tool. Для выбранных компонентов imports из `ai` являются `import type`: пакет нужен для TypeScript-типов, эти imports не запускают AI SDK и удаляются из итогового JavaScript. Хук `useChat`, провайдеры AI SDK и его серверный агентный цикл не подключаются. Если другой компонент использует runtime API, его зависимость оценивается отдельно перед добавлением.

Адаптер хранит соответствие по ID сообщения и toolCallId, чтобы stream deltas и повторное SSE подключение не создавали дубли. Стабильный ID сообщения назначает Crewbus при первом сохранении или `message_start`; это метаданные приложения, а не предполагаемое поле pi. Начало вызова инструмента отображается как `input-available`, успешный результат — `output-available`, ошибка — `output-error`. Отменённый незавершённый вызов получает явную отметку прерывания; его результат не выдумывается. Завершённые вызовы сохраняют фактический результат при остановке запуска. Серверные типы pi и сохранённые сообщения остаются каноническими; формат AI Elements не становится протоколом агента. Инструменты исполняются только на сервере.

Карточка Tool адаптируется к фактическим состояниям Crewbus: «Выполняется», «Готово», «Ошибка», «Прервано». Цвета и badges используют semantic tokens shadcn. Примерный состав экрана: Sidebar с диалогами; основная область с Conversation, Message и Prompt Input; панель тудушек; Dialog с провайдером и ключом, Model Selector для выбора модели. На узком экране панели открываются через Sheet. Эта версия не включает голос, вложения и артефакты; соответствующие действия Prompt Input не показываются.

### Референсы открытых harness’ов

Исследование [DeepSeek Harness, OpenCode, Goose, Agent Canvas и Lobe UI](../../research/2026-10-09-harness-ui-comparison.md) показало разные подходы: DeepSeek использует собственные React-примитивы, CSS Modules и токены темы; OpenCode — собственную систему на Solid/Kobalte; Goose — shadcn/Radix с собственной темой.

Объяснение запрета Tailwind в DeepSeek сохранено в том же исследовании: их ограничения служат единообразию и проверяемости стилей, которые пишут агенты. Отдельного технического обоснования против Tailwind источник не содержит. Для Crewbus сохраняем этот контекст и принципы владения темой; запрет Tailwind не принимается как требование проекта.

Предлагается определить токены и композиции Crewbus поверх выбранных shadcn/AI Elements. Для будущего гипервизора основной референс DeepSeek — отдельное дерево субагентов, их состояния и открытие дочернего разговора рядом с основным. Высокоуровневые модули DeepSeek связаны с Cordis и протоколом DSH; прямое использование его ui-primitives/ui-theme требует отдельной проверки переносимости. Смена UI-основы и добавление субагентов в MVP не согласованы.

### Безопасность registry-компонентов

Компоненты из shadcn registries добавляются в проект как исходники. `minimumReleaseAge` pnpm применяется к их npm-зависимостям, но не проверяет возраст или содержимое TSX/JSON, полученных по URL registry.

Поэтому перед добавлением выбирается явный registry и фиксируется ревизия upstream. Проверяются файлы компонентов, их registryDependencies и npm-зависимости; импортируются компоненты из проверенного снимка. В репозитории сохраняются сведения о происхождении: URL, commit/revision и SHA-256 импортированных upstream-файлов. Обновление идёт через проверяемый diff, без автоматической перезаписи компонентов по изменяемому URL.

shadcn CLI используется фиксированной выдержанной версией через pnpm с политикой проекта. Команды из документации с `@latest` не копируются в штатную установку. Npm-зависимости, добавленные registry, проходят ту же выдержку 14 дней и фиксируются точными версиями; версия исходников registry и версии npm-пакетов рассматриваются отдельно.

Сгенерированные файлы читаются до включения в приложение. Особое внимание: совместимость с Vite, отсутствие обязательных Next.js imports, серверных секретов и исполнения сырого HTML модели; корректные aliases, доступные формы и управление клавиатурой. Эта проверка дополняет проверку lockfile, а не заменяется ею.

### Провайдеры и ключи

На сервере создаётся коллекция провайдеров через `builtinModels({ credentials })` из pi-ai. Каталог провайдеров и моделей берётся из этой коллекции; собственного списка моделей и провайдерных адаптеров нет.

В MVP экран настройки показывает провайдеров, поддерживающих простой ввод API-ключа. Провайдеры, которым обязательны OAuth или дополнительные облачные параметры, не получают неработающую форму «один ключ». Их подключение можно расширить позже средствами pi.

Ключ записывается на сервере как `Credential` с типом `api_key`. Небольшой SQLite-адаптер реализует контракт pi `CredentialStore`: `read`, `list`, `modify`, `delete`. Операции изменения сериализуются по провайдеру. Приложение запускается одним серверным процессом на один том SQLite.

HTTP ответы возвращают только идентификаторы, названия и признак настроенного ключа. Сохранённый ключ не возвращается в браузер и не попадает в логи. Вводимый ключ не сохраняется в localStorage. Серверные данные содержат секреты: SQLite хранится в закрытом каталоге данных, доступном пользователю процесса. В MVP отдельного шифрования базы нет.

Выбор провайдера и модели записывается в диалог. Его можно поменять между запусками; текущий запуск использует зафиксированную при старте пару. Ключи хранятся отдельно от сообщений и конфигурации диалога.

### Агент и запуск

Каждому активному диалогу соответствует свой `Agent`. Он получает системные инструкции Crewbus, выбранную модель, историю сообщений и исключительно инструменты из нашего реестра. `streamFn` передаётся из pi-ai через `models.streamSimple.bind(models)`.

Системные инструкции требуют использовать инструмент для любых изменений тудушек, подтверждать выполненное действие по результату инструмента и явно сообщать об ошибках. Агент не утверждает, что умеет запускать других агентов, пока соответствующие инструменты не подключены.

Для инструментов выбирается `toolExecution: sequential`: порядок нескольких изменений списка задач должен быть однозначным.

Запуск имеет состояния `running`, `completed`, `failed`, `aborted`, `interrupted` и отдельную причину завершения. Повторная отправка сообщения в занятый диалог возвращает 409; интерфейс блокирует отправку до завершения или остановки. Каждый запрос старта содержит `clientRequestId`: повтор с тем же ID и телом возвращает ранее созданный запуск, даже если диалог занят или запуск уже завершён. Тот же ID с другим текстом возвращает 409. Проверка повторов предшествует проверке занятости. Уникальность пары `(chatId, clientRequestId)`, создание запуска и сохранение пользовательского сообщения обеспечиваются одной транзакцией до обращения к модели. События pi обновляют уже сохранённое сообщение, не добавляя его повторно.

Остановка вызывает `agent.abort()`. Диалог остаётся занятым до завершения обработки событий и сохранения конечного состояния; HTTP ответ на запрос остановки сам по себе не означает завершения. Остановка завершённого запуска не меняет его статус. Уже сохранённые изменения тудушек остаются выполненными. Перед изменением задачи инструмент проверяет AbortSignal; изменение и запись результата затем выполняются одной короткой SQLite-транзакцией. После её commit отмена не превращает выполненное действие в ошибку. В первой версии нет автоматического возобновления или повторного выполнения инструментов после ошибки.

Обработчик `finishTurn` ограничивает запуск 20 обращениями к модели. После двадцатого завершённого обращения следующий запрос не запускается; инструменты этого ответа завершаются по обычным правилам. Если требовалось продолжение, результат запуска — `failed` с причиной `turn_limit`; обычный финальный ответ на двадцатом обращении остаётся `completed`. Общий таймаут запуска — 5 минут; превышение вызывает отмену и результат `aborted` с причиной `timeout`. Ручная остановка даёт `aborted` с причиной `user_abort`, ошибка провайдера — `failed`, восстановление после остановки процесса — `interrupted`. Ограничения принадлежат менеджеру запусков, а не веб-интерфейсу.

### История и события

В SQLite сохраняются канонические сообщения pi с вызовами инструментов и их результатами. Системные инструкции хранятся отдельно как snapshot `systemPrompt` запуска и передаются в соответствующее поле Agent: в изученном API pi они не являются сообщением массива `AgentMessage[]`. Текстовый transcript для UI не используется для восстановления контекста модели.

`message_end` сохраняет завершённое сообщение. `agent_end` сохраняет итоговое состояние и статус запуска до завершения обработки. Изменение истории или статуса и запись соответствующего SSE-события происходят в одной транзакции; публикация клиентам — после commit. Подписчик pi возвращает Promise, чтобы агент ожидал сохранения. Ошибка записи останавливает запуск; успешное конечное событие клиенту не отправляется. Диалог освобождается после завершения ожидаемых подписчиков pi, а не при самом начале `agent_end`.

При старте сервера незавершённые запуски помечаются `interrupted`; автоматически не повторяются. Сохранённый результат todo-инструмента позволяет показать выполненное действие даже при сбое между commit изменения и событием pi о результате. Для восстановления допустимо дополнить каноническую историю этим фактическим результатом без повторного исполнения. Хвост с отсутствующими результатами или незавершённым ответом исключается из следующего контекста; в UI он остаётся с отметкой прерывания. Тудушки берутся из SQLite, а не из предположений модели; новый запуск после прерывания получает актуальное состояние через `todo_list` до любых изменений.

SSE передаёт текст ответа, начало и завершение инструментов, ошибки и итоговый статус. События имеют последовательный ID внутри запуска и сохраняются для повторного подключения. Клиент передаёт `Last-Event-ID`; для первого подключения после загрузки snapshot поддерживается параметр `after`. Заголовок имеет приоритет над параметром; при отсутствии обоих воспроизведение начинается с первого события. Cursor — неотрицательный целый ID в пределах данного запуска, невалидное значение возвращает 400. Подписка создаётся до чтения сохранённых событий; отправка идёт по ID с устранением дублей, чтобы закрыть гонку между воспроизведением и живым потоком.

Отключение браузера прекращает только подписку; агент продолжает принятый запуск. При перезагрузке `GET /api/chats/:id` возвращает согласованный snapshot: историю, актуальные тудушки, состояние последнего запуска, частичный ответ и cursor `lastEventId` этого запуска. Частичный ответ строится из сохранённых событий; snapshot читается в одной SQLite-транзакции. Клиент открывает SSE после этого cursor, поэтому уже показанные части ответа не доставляются повторно. Событие завершения содержит статус и причину; клиент закрывает EventSource после его получения. Для завершённого запуска сервер воспроизводит оставшиеся события и закрывает поток; если snapshot уже содержит конечное состояние, клиент поток не открывает. Поток не повторяет запрос к модели.

Полные аргументы и результат инструмента отображаются в раскрываемой карточке. Текст и данные отображаются средствами React, без исполнения HTML из ответа модели.

### Тудушки

Объект задачи: `id`, `chatId`, `title`, `completed`, `createdAt`, `updatedAt`. Идентификаторы генерируются сервером. Заголовок после удаления пробелов по краям содержит от 1 до 500 символов.

| Инструмент | Параметры | Результат |
| --- | --- | --- |
| `todo_create` | `title` | Созданная задача |
| `todo_list` | Необязательный `completed` | Задачи текущего диалога в порядке создания |
| `todo_update` | `id`, необязательные `title` и `completed`; хотя бы одно изменение | Обновлённая задача |
| `todo_delete` | `id` | ID удалённой задачи |

`chatId` привязывается на сервере при создании инструмента, модель не передаёт его. Чужой или отсутствующий ID возвращает ошибку инструмента. Аргументы описываются TypeBox-схемами pi; бизнес-валидация остаётся в сервисе тудушек.

Результаты выполненных todo-инструментов сохраняются по паре `(runId, toolCallId)`. Для изменяющего инструмента запись результата и изменение задачи атомарны. При повторном обращении с той же парой и аргументами возвращается сохранённый результат; с другими аргументами — ошибка без изменения данных. Это защита от повторного применения уже выполненного вызова, а не механизм возобновления запуска. Результаты списка фиксируются как фактический snapshot на время вызова.

Панель отображает актуальный список и позволяет добавить, переименовать, завершить и удалить задачу вручную. HTTP API и инструменты вызывают один сервис тудушек. Пока агент работает, ручное редактирование задач этого диалога отключено и отвергается сервером с 409. После успешного инструмента или ручного изменения UI обновляет список.

### Минимальные HTTP контракты

- `GET /api/providers` — провайдеры с простым API-key входом и признак настройки.
- `GET /api/providers/:id/models` — доступный каталог моделей провайдера.
- `PUT /api/providers/:id/credential` — сохранить `{ key }`; ключ не возвращается; 409 при активном запуске с этим провайдером.
- `DELETE /api/providers/:id/credential` — удалить ключ, 409 при активном запуске с этим провайдером.
- `GET /api/chats` и `POST /api/chats` — список и создание диалогов.
- `GET /api/chats/:id` — согласованный snapshot диалога, истории, тудушек и последнего запуска с `lastEventId`.
- `PATCH /api/chats/:id` — изменить выбранные `providerId` и `modelId`, 409 при активном запуске.
- `POST /api/chats/:id/runs` — принять `{ text, clientRequestId }`, вернуть 202 с `runId`.
- `GET /api/runs/:id/events?after=:eventId` — SSE; при reconnect используется `Last-Event-ID`.
- `POST /api/runs/:id/abort` — остановить; повторный запрос безопасен.
- `GET` и `POST /api/chats/:id/todos`, `PATCH` и `DELETE /api/chats/:id/todos/:todoId` — ручная работа с задачами.
- `GET /api/health` — готовность HTTP сервера и SQLite без вызова внешней модели.

Тела HTTP запросов проверяются схемами Fastify. Максимальный текст одного сообщения — 16 000 символов. Неизвестные объекты возвращают 404, невалидные параметры — 400. Отсутствие ключа блокирует запуск до обращения к провайдеру. Ошибки авторизации, лимитов и сети отображаются в чате; секреты и заголовки авторизации исключаются из сообщений и логов. Ошибка контекстного окна предлагает новый диалог: автоматическое сжатие истории в MVP не входит.

## Версии и защита зависимостей

Исходные версии выбраны по исследованию от 2026-10-09 и сохраняются для воспроизводимости. Перед установкой и созданием lockfile проверяются публикации, integrity, известные уязвимости и фактические настройки pnpm; выдержка вычисляется на дату установки, а не на дату написания документа.

Node.js: фиксируем `24.21.0`, ветка 24 LTS. Она подходит под требования изученной версии pi (`node >=22.19.0`). На момент исследования в окружении был Node 22; реализация и проверки выполняются на Node 24.

pnpm: фиксируем `12.6.0` в `packageManager`. Релиз опубликован 2026-09-22 и проходит выдержку на дату документа. Менеджер пакетов устанавливается фиксированной версией; загрузчик и пакет проверяются по integrity, без bootstrap через произвольный shell-скрипт.

Исходные версии pi: `@earendil-works/pi-ai@0.87.1` и `@earendil-works/pi-agent-core@0.87.1`, опубликованы 2026-09-22. В исследовании от 2026-10-09 последним обнаруженным релизом был `1.1.0`, опубликованный 2026-10-07; на 2026-10-12 он также не проходит правило 14 дней. Версия `0.87.1` проверена по исходникам тега, а не по API текущего `main`. Полное дерево зависимостей должно отдельно пройти резолв и проверку политики при создании lockfile. Смена pi на другой релиз требует проверки API и обновления плана, а не происходит автоматически после истечения выдержки.

В `pnpm-workspace.yaml` закладывается следующая политика:

```yaml
packages:
  - apps/*
  - packages/*

minimumReleaseAge: 20160
minimumReleaseAgeStrict: true
minimumReleaseAgeIgnoreMissingTime: false
minimumReleaseAgeExclude: []

trustPolicy: no-downgrade
trustPolicyExclude: []
trustLockfile: false
blockExoticSubdeps: true

strictDepBuilds: true
dangerouslyAllowAllBuilds: false
allowBuilds: {}
verifyDepsBeforeRun: error

saveExact: true
engineStrict: true
```

`20160` — 14 дней в минутах. При отсутствии подходящей выдержанной версии установка завершается ошибкой; fallback на свежий релиз запрещён. Отсутствие времени публикации тоже считается ошибкой. Проверка применяется к прямым и транзитивным зависимостям, включая записи уже существующего lockfile.

Build-скрипты зависимостей по умолчанию не разрешены. Если выбранной версии Vite необходим скрипт esbuild, сначала проверяются конкретная версия и скрипт; в `allowBuilds` добавляется разрешение только для точной версии. Неизвестные скрипты останавливают установку. Другие способы обхода, например глобальный `ignore-scripts` вместо проверки политики или `dangerouslyAllowAllBuilds`, не используются в штатной установке.

Прямые внешние зависимости закрепляются точными версиями; внутренние используют `workspace:*`. Git, URL и произвольные tarball-зависимости не добавляются. `pnpm-lock.yaml` хранится в Git. CI и Docker устанавливают зависимости через `pnpm install --frozen-lockfile`, сохраняя проверку политики. Изменение lockfile проверяется как изменение кода.

Дополнительная проверка: `pnpm audit --prod --audit-level=high`. Она проверяет известные уязвимости и дополняет выдержку; результат не заменяет возрастную политику. Ошибка проверки не игнорируется автоматически.

## Этапы реализации и проверяемые результаты

1. **Окружение и зависимости.** Node 24, pnpm, workspace, политика защиты, точные версии, lockfile, Tailwind 4 и shadcn. Проверенные снимки выбранных компонентов AI Elements с записью происхождения. Чистая установка проходит политику без исключений выдержки; сервер отвечает на health, веб-приложение собирается.
2. **Настройки и хранилище.** SQLite с миграциями, CredentialStore, каталог pi, создание диалогов. После перезапуска ключ остаётся настроенным, но HTTP API не возвращает его; диалоги сохраняются.
3. **Сквозной чат.** Менеджер запусков, pi Agent, сохранение сообщений, SSE, отправка и остановка в UI. Ответ отображается по мере генерации; перезагрузка браузера не запускает повторное обращение к модели.
4. **Тудушки как инструменты.** Общий сервис, четыре инструмента, панель и карточки вызовов. Создание, завершение и удаление задачи через чат изменяют SQLite и UI; другие диалоги не затрагиваются.
5. **Ошибки и восстановление.** Неавторизованный провайдер, двойная отправка, отмена, прерывание процесса, повторное SSE подключение, лимиты. Нет автоматического повторения изменений и зависших состояний после перезапуска.
6. **Упаковка.** Многоэтапный Docker build на Node 24 с фиксированной версией образа и digest, запуск от непривилегированного пользователя, persistent volume, healthcheck, README. Контейнер обслуживает веб и API одним портом; пересоздание с тем же томом сохраняет состояние.

Docker Compose по умолчанию публикует порт только на `127.0.0.1`; процесс внутри контейнера слушает `0.0.0.0`. Интернет-доступ и многопользовательская авторизация — отдельная задача, не неявное свойство этого MVP.

## Проверки и критерии готовности

Для автоматических тестов используется `fauxProvider` pi: сценарии не требуют реального API-ключа и не расходуют платные токены. Тесты проверяют поведение, а не повторяют внутреннюю реализацию.

- Чистая установка с frozen lockfile соблюдает выдержку, trust policy и правила build-скриптов.
- В агент зарегистрированы только четыре инструмента тудушек.
- Выбор двух разных поддерживаемых провайдеров использует один и тот же код создания агента.
- Сохранение, замена и удаление ключа работают; ключ отсутствует во всех HTTP ответах и логах.
- Диалоги и задачи восстанавливаются после перезапуска; задачи из разных диалогов изолированы.
- Агент выполняет цепочку: создать задачу, прочитать список, завершить, удалить. UI показывает реальные результаты.
- Невалидный заголовок, чужой ID и неизвестный инструмент не изменяют хранилище.
- Двойной запрос старта с одним `clientRequestId` создаёт один запуск; другой запрос в занятый диалог получает 409.
- Остановка и таймаут прекращают дальнейшую генерацию; интерфейс возвращается в доступное состояние.
- Пропущенные SSE события восстанавливаются без дублей; смена диалога не смешивает потоки.
- Перезапуск сервера помечает активный запуск прерванным и не повторяет уже выполненный инструмент. Сбой после commit изменения задачи, но до события pi о результате сохраняет реальное изменение и позволяет показать его сохранённый результат.
- Snapshot истории и cursor согласованы; подключение после snapshot и повторное SSE подключение сохраняют частичный текст без удвоения. Получение конечного события прекращает автоматические reconnect клиента.
- Повтор `clientRequestId` с другим текстом возвращает 409; повтор выполненного todo-вызова не создаёт второе изменение. Достижение лимита, таймаут и обычное завершение различаются в UI.
- Browser smoke test проходит путь от настройки провайдера до изменения задачи и перезагрузки страницы.
- Registry-компоненты имеют записанное происхождение и проходят проверку исходников; их npm-зависимости не обходят правило выдержки.
- UI работает с клавиатурой, сохраняет ручное положение прокрутки при стриминге и правильно отображает выполнение, результат, ошибку и прерывание инструмента. На узком экране доступны чат, настройки и задачи.
- Адаптер pi → AI Elements сохраняет ID и порядок сообщений, не дублирует результаты после reconnect и не выполняет инструменты на клиенте. Для чата не нужен `useChat` или серверный runtime AI SDK.
- TypeScript проверки, тесты сервера/агента, сборка клиента и Docker smoke test проходят на Node 24.

Один короткий ручной тест с настоящим выбранным провайдером проверяет фактическую совместимость модели; автоматические тесты остаются независимыми от сети провайдера.

## Основа для будущего управления агентами

Реестр инструментов — единственное место подключения возможностей главного агента. В следующей версии он сможет получить инструменты наподобие `agent_spawn`, `agent_status`, `agent_send`, `agent_cancel`.

В предлагаемой архитектуре менеджер запусков отделён от веб-транспорта, а события несут идентификаторы диалога, запуска и вызова инструмента. Это создаёт основу для дочерних запусков; новые типы событий и интерфейс управления будут определены следующей спецификацией. Конкретный протокол дочерних агентов и их песочницы в текущей версии не реализуются.
